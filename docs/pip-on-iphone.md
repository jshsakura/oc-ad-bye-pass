# 아이폰에서 작은 창 (PiP) — 알아낸 것과 헛짚은 것

2026-08-12, 실기기(아이폰 · Orion)에서 v0.10.17 부터 v0.10.39 까지 스물세 번 배포하며
알아낸 것을 남긴다. **여기 적힌 "측정" 은 전부 기기 로그에서 읽은 것이고, 추측은
추측이라고 적었다.** 다음 사람이 같은 곳을 두 번 파지 않기 위한 문서다.

## 한 줄 요약

> **작은 창은 진짜 사용자 제스처 안에서만 열린다.** 나머지는 전부 그 사실을 몰라서
> 생긴 소동이었다.

## 플랫폼이 정한 것 — 바꿀 수 없는 부분

`webkitSetPresentationMode('picture-in-picture')` 는 **오류도 안 내고, 이벤트도 정상으로
쏘고, 창은 안 띄운다.** 애플이 우리와 똑같은 재현 절차(백그라운드 전환 시점에
`play()` 후 호출)에 직접 답한 것이 있다.

> "사용자 상호작용 없이는 안 된다. 오직 사용자 상호작용에 대한 응답으로만 PiP 를
> 시작하라. 프로그램적으로는 절대 안 된다."
> — [Apple Developer Forums #819235](https://developer.apple.com/forums/thread/819235),
> [WebKit Bugzilla #172051](https://bugs.webkit.org/show_bug.cgi?id=172051)

WebKit 의 사용자 활성화(transient activation)는 탭 이후 **몇 초** 살아 있고 비동기
경계를 넘지 못한다([WebKit 블로그](https://webkit.org/blog/13862/the-user-activation-api/)).
**같은 코드가 어떤 때는 되고 어떤 때는 안 되던 이유가 이것이다** — 직전에 탭이 있었으면
활성화가 살아 있었고, 없으면 없었다. 이 사실을 모르고 다른 원인을 여러 번 쫓았다.

따라서 실제로 창을 여는 경로는 셋뿐이다.

| 경로 | 신뢰도 | 비고 |
|---|---|---|
| PiP 버튼 탭 | **확실** | 진짜 탭. 데스크톱 사파리에서도 실측으로 창이 열림 |
| 아래에서 위로 쓸어 나가기 | **높음** | 나가는 제스처 자체. 터치가 시스템보다 먼저 페이지에 닿는다 |
| 나가는 순간의 호출 | 운 | 직전 탭의 활성화가 아직 살아 있을 때만 |

## 기기에서 측정한 사실

전부 진단 패널의 기록에서 읽은 것이다.

1. **나가는 신호가 올 때 영상은 이미 멈춰 있다.** 엔진이 페이지보다 먼저 세운다.
   그래서 "멈춰 있으면 넘어간다" 는 판단은 매번 걸렸다 (`skip:paused`).
2. **되살린 뒤 요청하면 창이 열린다** — `called:from-inline` → `모드 → picture-in-picture`.
   여러 차례 재현됐다.
3. **유튜브가 5초쯤 뒤 창을 끌어내린다.** `54:14.855 → 54:19.889`. 이건 유튜브가
   `webkitpresentationmodechanged` 를 듣고 하는 일이다.
4. **유튜브가 "페이지가 숨겨졌다"는 사실을 알면 플레이어를 통째로 내린다.** 요소가
   0초·paused·`webkitSupportsPresentationMode === false` 로 리셋된다
   (`28:12.665 시간=0.0`). **그래서 시야 거짓말은 반드시 유지해야 한다.**
5. **작은 창이 떠 있는 동안 iOS 는 페이지를 "보이는 중" 으로 친다.** 즉 창이 열린 것과
   사용자가 돌아온 것이 구분되지 않는다. 구분되는 것은 **포커스** 뿐이다.
6. **복귀와 끌어내림은 같은 이벤트로 온다.** 페이로드도 같다.

## 지금 남아 있는 장치 (셋)

1. **시야 거짓말** (`src/main/backgroundPlay.ts`) — 4번 때문에 필수. 나갈 때의
   `visibilitychange` 를 삼키고 우리 쪽으로만 사설 이벤트로 다시 알린다. 복귀 때는
   ISOLATED 가 "진짜 돌아왔다" 고 알려주면 그때 한 번만 통과시킨다 — 그 한 번이
   플레이어에게 다시 그리라는 신호이고, 없으면 **복귀 때마다 검은 화면**이 남는다.
2. **리스너 차단** (`src/main/deafenPlayer.ts`) — 유튜브가 `webkitpresentationmodechanged`
   를 **등록조차 못 하게** 한다. 3번(5초 끌어내림)이 이걸로 사라졌다(로그로 확인).
   이벤트를 막는 방식은 안 된다: 같은 요소의 리스너는 캡처/버블이 아니라 **등록
   순서**로 돌기 때문에, 유튜브가 먼저 붙었으면 우리가 막아도 이미 늦다.
3. **모드 변경 센서** (`src/isolated/pip.ts`) — 창이 실제로 열렸는지 아는 **유일하게
   정직한 신호**. 호출의 반환값은 아무것도 증명하지 못한다.

## 헛짚은 것 — 다시 하지 말 것

| 시도한 것 | 왜 지웠나 |
|---|---|
| 표시 모드 이벤트 삼키기 | 유튜브가 자기 상태를 갱신 못 해서 "playing in picture in picture" 카드가 페이지에 남는다. 등록 순서에도 진다 |
| 페이지의 `inline` 호출 거절 (`holdPresentation`) | 정작 창을 닫던 호출은 **우리 세계**에서 나갔다. 페이지 프로토타입을 막아봐야 못 잡는다. 대신 플레이어 상태를 영구히 어긋나게 만들었고, 플래그가 남으면 그 페이지는 영영 inline 복귀 불가가 됐다 |
| 밀려나면 다시 열기 (최대 3회) | 복귀 이벤트와 구분이 안 되니 **돌아온 사용자 앞에서 창을 세 번 다시 열었다.** 그 3회가 "복귀 후 3초 검은 화면" 이었다 |
| 350ms 재시도 루프 + 전체화면 승격 | 페이지가 얼면 돌지 않고, 안 얼면 이미 필요 없다 |
| 탭 하나를 전체화면으로 소비 (arming) | 스크롤도 `touchend` 로 끝나서 영상을 잡고 쓸어내리면 전체화면이 됐다. 작은 창을 원한 사람에게 전체화면을 주는 것이기도 하다 |
| `blur` 를 나가는 신호로 쓰기 | 팝업 열기·주소창 터치·우리 버튼 누르기 전부 `blur` 다. 진단 버튼을 누르면 영상이 PiP 로 들어갔다 |
| 나가 있는 동안 시야 거짓말 끄기 | 4번 — 플레이어가 통째로 내려간다. **백그라운드 재생까지 같이 죽는다** |
| 비디오 요소 복제/디코이 | 유튜브는 MSE `blob:` 로 재생한다. `cloneNode` 는 `ERR_FILE_NOT_FOUND` 로 죽는다 ([jumpcutter#2](https://github.com/WofWca/jumpcutter/issues/2)) |
| `navigator.audioSession` · 무음 오디오 루프 · PWA standalone | 백그라운드 실행과 무관하다. PWA 는 오히려 프로세스가 통째로 정지된다 |

## 어디에 버튼을 그리나 (0.25.0)

**WebKit 이거나 폰일 때만.** 위의 모든 것이 아이폰에서 잰 사실이고, 그 사실은
다른 곳으로 옮겨가지 않는다 — 데스크톱 크롬은 우클릭 두 번과 주소창 미디어 컨트롤,
파이어폭스는 영상 위 자체 토글로 PiP 가 이미 열린다. 거기서 우리 버튼은 플레이어
위에 뜬 중복이었고 "거슬린다" 는 신고가 그것이었다.

판정은 `src/ui/device.ts` 의 `needsPipButton` 하나다. 콘텐츠 스크립트는 그 값이
거짓이면 버튼을 안 그리고, 팝업은 스위치를 아예 보이지 않으며, 진단 패널은
`PiP 버튼: 그리지 않음 — 브라우저 자체 PiP 사용` 이라고 적는다. "버튼이 사라졌다" 는
신고가 오면 그 줄부터 읽는다.

e2e 는 `test.use({ screen: PHONE_SCREEN })` 으로 데스크톱 Chromium 을 폰으로
만들어 돌린다. 화면 크기를 안 주면 데스크톱이고, 데스크톱에서는 버튼이 없는 것이
맞는 결과다.

## 진단하는 법

폰에는 콘솔이 없다. 팝업 → **진단** 이 전부다.

- `1계층 주입` — `차단됨` 이면 그 페이지에 1계층이 아예 없다
- `PiP 지원(이 영상)` — `아니오` 면 아무리 눌러도 안 열린다
- `자동 PiP` — 어느 신호가 왔고 호출이 수락/거절/부재였는지
- `--- 기록 ---` — 페이지를 옮겨도 남는다(스토리지에 누적). 여기가 진짜 답이 있는 곳

읽는 요령: `모드 바뀜 → picture-in-picture` 가 있으면 창이 실제로 열린 것이다.
`called` 만 있고 그게 없으면 **활성화가 만료된 것**이고, 그건 코드로 못 고친다.

## 아직 모르는 것

- 홈 제스처를 넓힌 것(아래 60px, 위로 16px)이 실기기에서 얼마나 잡히는지
- `모드는 picture-in-picture 인데 창이 없는` 유령 상태를 JS 로 확인할 방법 — 없다는
  것이 조사 결론이다. `inline` 로 한 번 되돌리는 것이 유일한 리셋이고 효과는 미확인
- iOS 설정의 "자동으로 PiP 시작" 이 명시적 호출에도 영향을 주는지 (유력하나 미확인,
  JS 로는 감지 불가)
